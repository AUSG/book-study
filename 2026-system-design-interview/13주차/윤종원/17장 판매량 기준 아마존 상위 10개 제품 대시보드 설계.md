# 17. 판매량 기준 아마존 상위 10개 제품 대시보드 설계
- 상위 K 문제의 흔한 유형의 대시보드
- 분석을 논의할 때 흔히 다룰 수 있는 주제이거나 독립적인 면접 질문이 될 수 있다
	- 온라인 쇼핑몰 앱에서 판매량이나 수익 기준 최고 판매나 최저 판매 제품
	- 온라인 쇼핑몰 앱에서 가장 많이 본 제품이나 가장 적게 본 제품
	- 앱 스토어에서 가장 많이 다운로드된 앱
	- 유튜브 같은 비디오 앱에서 가장 많이 본 동영상
	- 음악 앱에서 가장 인기 있는 노래나 인기 없는 노래
	- 로빈후드나 ETRADE 같은 거래소에서 가장 많이 거래된 주식
	- SNS에서 가장 많이 전달된 게시물

## 17.1 요구사항
- 다음과 같은 질문이 필요하다
	- 동점은 어떻게 처리하나?
		- 높은 정확도가 중요하지 않을 수 있으므로 동점이면 아무거나 선택해도 될 수도 있다
	- 어떤 시간 간격을 고려하나?
		- 일, 주, 연도 등
	- 사용 사례는? 
		- 이는 정확도, 일관성, 지연 시간을 결정한다.


- 실시간 -> 리소스가 많이 필요. 람다 아키텍처 등으로 최근 몇 시간 동안의 근사 판매량과 순위를 제공하는 최종적으로 일관된 솔루션과 몇 시간 이전 시간대의 정확한 수치를 제공할 수 있다
- 정확도를 낮추는 대신 더 높은 확장성, 더 낮은 비용, 더 낮은 복잡성, 더 나은 유지보수성을 얻는 것을 고려할 수 있다.
- 특정 기간 내의 특정 상위 K 목록을 해당 기간 지난 후 최소 몇 시간 후에 계산할 것으로 예상하므로 일관성은 문제가 되지 않는다.
- 목록 생성에 시간이 걸리는 건 당연하므로 낮은 지연시간도 문제가 되지 않는다.


- 상위 K만 필요한가? 임의의 수의 제품 판매량과 순위가 필요한가?
- 상위 K 목록에 판매 수가 필요한가? 순위만 필요한가?
- 판매 후 발생하는 이벤트 고려해야 하나? 환불, 교환 등
- 확장성 관련 질문들
	- 판매 거래 비율은 어떻게 되나?
	- 상위 K 대시보드 요청 비율은 어떻게 되나?
	- 제품은 몇 개나 있나?


- 하루 100억 건 판매 트래픽
- 이벤트당 1KB -> 쓰기 속도 하루 10TB
- 대시보드는 직원만 보니 요청 비율은 낮다
- 약 100만 개 제품이 있다고 가정

## 17.2 초기 구상
- 첫 번째 생각
	- 이벤트를 HDFS나 ES 등에 기록하고 
	- 특정 기간 내 목록이 필요할 때 Map Reduce, Spark, ES 쿼리 등으로 계산하는 것
	- 그러나 이는 계산 집약적으로 시간이 너무 오래 걸릴 수 있다
	- 또한 이 외에 다른 목적이 없다면 이를 위해서 로그를 장기 보관하는 것 또한 낭비다
	- 초당 수백만 건 요청 -> 연간 수 PB
- 따라서 상위 K 목록 계산 전에 데이터 전처리가 필요하다
	- 주기적 집계 수행
	- 제품 판매량 계산, 시간, 일, 주, 월, 연 버킷팅
- 이렇게 하면 상위 K 목록이 필요할 때 다음만 하면 된다
	- 적절한 버킷을 골라 이들끼리 합산하고 정렬한다

	- 정확한 숫자가 준비되면 즉시 이용할 수 있게 스트리밍 데이터를 배치가 덮어쓸 수 있게 한다.

## 17.4 집계 서비스
![](files/Pasted%20image%2020260726162254.png)
- 람다 아키텍처에 적용할 수 있는 초기 최적화는 판매 이벤트에 대한 집계 수행하고, 이를 스트리밍과 배치 파이프라인에 전달하는 것
- 이렇게 하면 스트리밍, 배치 클러스터 크기를 줄일 수 있다
- 파이프라인의 결과는 RDBMS에 쓰고, 대시보드도 이를 쿼리해서 쓴다.

### 17.4.1 제품 ID별 집계
- 정확한 타임스탬프는 중요하지 않으므로 집계할 수 있다
- 혹은 시간별 특정 시간 간격이 중요하다면 시간 쌍을 일치시켜 집계할 수도 있다.

### 17.4.2 호스트 ID와 제품 ID 매칭
- 집계 서비스는 제품 ID별로 분할할 수 있어 각 호스트가 특정 ID 세트를 집계하는 역할을 맡게 된다
- 간소화를 위해 (host ID, product ID) 맵을 수동으로 관리할 수도 있다.
- 이 구성에는 여러 실행 방안이 있다.
	1. 서비스 소스 코드에 포함된 구성 파일, 파일 변경할 때마다 전체 클러스터 재시작
	2. 공유 객체 스토어에 올려두고, 각 호스트는 시작 시 이 파일을 읽고 메모리에 저장. 제품 ID를 업데이트할 수 있는 엔드포인트도 제공해야 한다. 파일을 변경할 때 다른 제품 ID를 소비할 호스트에서 이 엔드포인트를 호출
	3. SQL이나 레디스에 저장
	4. 사이드카 패턴. 호스트가 사이드카에 페치 요청을 한다.

- 보통 옵션 2, 4 중 하나를 써 전체 클러스터 재시작을 막는다
- 아래 이유로 DB보다는 파일을 선택
	- YAML, JSON 등은 해시 맵으로 파싱이 쉽다. 
	- 구성 파일 수는 매우 작으므로 각 호스트가 전체 파일을 페치할 수 있다. DB의 장점이 필요 없다
	- 구성이 자주 바뀌지 않는다.

### 17.4.3 타임스탬프 저장
- 정확한 타임스탬프 저장이 필요하면 이는 판매 서비스에서 처리해 책임을 분리해야 한다
- 상위 K 외에도 수많은 분석 파이프라인이 있을 거고, 다른 서비스와 무관하게 이런 파이프라인을 개발하고 폐기할 수 있는 완전한 자유가 있어야 한다
- 다른 서비스가 이러한 분석 서비스의 종속성이 되어야 하는지 결정할 때 주의해야 한다.

### 17.4.4 호스트의 집계 프로세스
- 집계 호스트는 제품 ID를 키로, 수량을 값으로 하는 해시 테이블을 포함
- 카프카 토픽에 체크포인팅을 하고, 이를 레디스에 쓴다
- 체크포인트는 집계된 이벤트 ID로 구성된다.
- 집계 서비스는 파티션 수보다 더 많은 호스트를 가질 수 있지만, 집계가 간단하고 빠른 작업이므로 필요하지 않다


- 각 호스트는 다음을 반복적으로 수행
	- 토픽에서 이벤트 소비
	- 해시 테이블 업데이트
- 집계 호스트는 설정된 주기나 메모리가 부족할 때 더 빠른 시점에 해시 테이블 플러시할 수 있다
	1. 집계된 이벤트를 `Flush`라는 이름의 카프카 토픽으로 생성하고, 이를 이벤트로 쓴다. (product ID, earliest timestamp, latest timestamp, number of sales 등의 필드를 지닌 제품 ID 집계 튜플 목록으로 구성
	2. CDC로 각 목적지는 다음 소비자를 가짐
		- 집계된 이벤트를 HDFS에 쓴다
		- complete 상태의 튜플 체크포인트를 레디스에 쓴다
		- 이를 반복한다.
- Flush라는 토픽이 없으면 특정 목적지에 집계된 이벤트 쓰다가 실패하면 재집계해야 한다
- 두 개의 체크포인트가 필요한 이유는? -> 일관성을 유지하기 위한 여러 가능한 알고리즘 중 하나
	- 1단계 중 실패하면 다른 호스트가 플러시 이벤트를 소비하고 쓰기를 수행할 수 있다
	- 2-a에서 실패하면 HDFS 성공 여부를 모르므로 쓰기 성공인지 재시도해야 하는지 확인할 수 있지만 HDFS 읽기도 비용이 많이 든다.
		- 다만 호스트 실패는 드물기 때문에 괜찮을 수도 있다
	- 이런 부분이 우려된다면 1분에서 몇 분 사이의 모든 처리 중 체크포인트를 읽는 주기적인 작업으로 실패 복구 메커니즘을 구현할 수도 있다
- 실패 복구 메커니즘 자체도 멱등성을 가져야 한다.


- 내결함성을 고려해야 한다
	- 모든 쓰기는 실패할 수 있다
	- 쓰기 이벤트 응답이 200이어도 자잘한 오류가 발생할 수 있다.
	- 따라서 HDFS와 스트리밍 파이프라인에 별도의 체크포인트를 쓴다
	- 쓰기 이벤트에는 ID가 있으므로 필요하면 중복 제거를 수행할 수 있다.


- 여러 서비스에 이벤트를 써야할 때 일관성 없음을 방지하는 방법
	1. 각 서비스에 쓰기 후 체크포인트 수행
	2. 일관성 없음 허용
	3. 주기적 감사로 일관되지 않은 데이터를 버리고 재처리
	4. 2PC, 사가 패턴, CDC, Tx outbox 패턴

## 17.5 배치 파이프라인
![](files/Pasted%20image%2020260728210557.png)
- 증가하는 간격으로 집계, 롤업 작업으로 구성된다
- 시간별, 일별, 주별, 월별, 연도별로 롤업
- 100만 개의 제품 ID가 있다면
	1. 시간별 롤업은 하루에 2,400만 행 -> 주에 1억 6,800만 행
	2. 월별 롤업은 월에 2,800만 ~ 3,100만 행 -> 연간 3억 3,600만 ~ 3억 7,200만 행
	3. 일별 롤업은 주에 700만 행 -> 연간 3억 6,400만 행
- 10개의 64비트 열 가진 4억 행 -> 32GB
- 이는 단일 호스트에서 처리 가능


- 각 롤업에서 수를 내림차순으로 정렬하고 상위 K, 유연성을 위해 K * 2개의 행을 대시보드에 표시할 수 있다.

![](files/Pasted%20image%2020260728212615.png)
- 각 롤업마다 하나의 DAG, 총 4개의 DAG가 있다
	1. 시간별보다 큰 모든 롤업에서는 종속 롤업 실행이 성공적으로 완료되었는지 확인해야 함. 이는 비용이 많이 드는 SQL 쿼리 포함
	2. 하이브나 SQL 쿼리 실행해 수를 내림차순 합산하고, 결과를 batch table에 쓴다
	3. speed_table에서 해당 행을 삭제. 
	4. 새로운 batch_table 행을 사용해 적절한 상위 K 목록 생성하거나 재생성


## 17.6 스트리밍 파이프라인
- 스트리밍 파이프라인의 목적은 배치 파이프라인이 아직 제공하지 않은 수와 상위 K 목록을 제공
- 스트리밍 파이프라인은 배치보다 훨씬 빠르게 수치 계산해야 하며, 근사 기법을 쓸 수 있다.

### 17.6.1 단일 호스트의 해시 테이블과 최대 힙
- 첫 번째 시도는 해시 테이블 사용하고 크기 K의 최대 힙 써서 빈도수 정렬

### 17.6.2 여러 호스트로의 수평적 확장과 다중 계층 집계
![](files/Pasted%20image%2020260728213638.png)
- 중간 열의 두 호스트는 상위 호스트에서 (product, hour) 수를 합산하고 오른쪽 열의 최대 힙은 중간 열의 상위 호스트에서 (product, hour) 수를 집계한다.
- 첫 번째 계층의 호스트와 최종 해시 테이블 호스트 사이에 더 많은 계층을 넣어 어떤 호스트도 처리할 수 있는 것보다 많은 트래픽을 받지 않게 한다
- 다중 집계 서비스 구현의 복잡성을 집계 서비스에서 스트리밍 파이프라인으로 옮기는 것

- 제품 ID와 타임스탬프로 집계하는 이유는?
	- 상위 K 목록에는 시작 시간, 종료 시간이 있는 기간이 있음
	- 각 판매 이벤트가 정확한 시간 범위에 집계되어야 함
- 가장 작은 기간 (시간 범위)로 집계하면, 어떤 이벤트는 전체 클러스터 통과하는 데 몇 초밖에 걸리지 않을 것이므로 클러스터에서 1시간 이상 된 키는 거의 없을 것이다
- 각 제품 ID는 고유한 키를 가지고, 각 키에 시간 범위가 추가되므로 키의 수가 제품 수의 두 배보다 많을 가능성은 낮다


- 기간이 끝난 후 1분, 시간이 끝난 후 최종 계층의 호스트는 힙을 SQL speed_table에 쓰고, 대시보드는 상위 K 목록을 표시할 준비가 된다
- 전체 계층을 통과하는 데 1분 이상 소요될 수 있고, 이때 최종 호스트는 업데이트된 힙을 speed_table에 쓸 수 있다
- 1분을 기다리는 대신 이벤트가 호스트를 통과할 때마다 추적하고, 관련된 이벤트가 모두 최종 호스트에 도달한 후에만 최종 호스트가 힙을 speed_table에 쓰게 트리거하는 시스템도 구현할 수 있다
- 그러나 이는 지나치게 복잡할 수 있고, 모든 이벤트가 완전히 처리되기 전에 대시보드가 근사치 표시하는 것을 방해한다.

## 17.7 근사
![](files/Pasted%20image%2020260728214821.png)
- 더 낮은 지연 달성하려면 집계 서비스 계층 수를 줄여야 함
- 위 사진에서는 최대 힙으로만 구성된 계층이 있다. -> 더 빠른 업데이트, 더 낮은 지연. 정확성을 희생
- 더 느리고 매우 정확한 집계는 배치 파이프라인에 의존


- 최대 힙을 별도 호스트에 두는 이유는 -> 시스템 확장 및 축소를 고려했을 때 해시 테이블 호스트 수는 자주 변경될 수 있지만 활성 최대 힙 호스트, 복제본은 항상 하나뿐 -> 해시 테이블 호스트와 최대 힙 호스트에 별도의 도커 이미지를 가질 수 있음


- 그러나 이로 생성된 상위 K 목록은 부정확할 수 있다
- 최대 힙을 두고 최대 힙을 병합할 수는 없다. 최종 최대 힙이 실제로 상위 K 제품을 포함하지 않을 수 있기 때문

### 17.7.1 카운트-민 스케치

## 17.9 카파 아키텍처 접근 방식
- 스트리밍 데이터 처리하기 위한 아키텍처 패턴, 단일 기술 스택으로 배치와 스트리밍 모두 처리
- 데이터 저장하기 위해 카프카와 같은 append only 로그 사용하고, 스트림 처리와 사용자가 쿼리할 수 있는 데이터베이스에 저장하는 과정을 거친다.

### 17.9.1 람다 vs. 카파 아키텍처
- 람다는 복잡하다
- 배치, 스트리밍 계층이 따로 존재하며 그로 인한 부담 + 비용도 발생


- 카파는 람다를 단순화한 것으로 스트리밍만 있고 배치는 없다
- 서빙 계층은 스트리밍 계층에서 계산된 데이터 제공
- 모든 데이터는 메시징 엔진에 삽입된 직후 읽히고 변환되어 처리된다
- 낮은 지연 시간 + 실시간 데이터 처리에 적합
- 성능을 위해 정확도를 트레이드오프할 수도 있고, 이런 트레이드오프 없이 매우 정확한 데이터를 계산할 수도 있다.


- 그 외에도 배치 작업이 스트리밍에 비해 갖는 단점은 개발 + 운영 부담이 훨씬 높다는 것
- HDFS 등을 쓰는 배치 작업은 적은 양의 데이터도 최소 몇 분은 걸린다
	- HDFS는 지연 시간을 희생하고 높은 처리량을 얻기 때문이다


- 또한 배치 작업 실패는 개발, 테스트, 운영 등에서 실질적으로 불가피하고, 배치 작업이 실패하면 다시 실행해야 함
- 배치 작업을 기다리는 시간을 줄이기 위한 일반적인 기법 중 하나는 여러 단계로 나누는 법


- 전반적으로 배치 오류는 스트리밍 오류보다 비용이 많이 든다
- 배치 버그 하나가 전체 작업 실패로 이어질 수도 있다


- 카파가 람다에 비해 갖는 또 다른 장점은 상대적 단순성이다
- 카파는 단일 프레임워크


- 카파의 고려사항은 HDFS와 달리 Kafka에 대용량의 데이터 저장하는 건 비용이 많이 들고, 몇 PB 이상으로 확장하는 것은 불가능
- 카프카는 Log Compaction으로 무한 보존을 제공하므로 최신 값만 유지하고, 이전 값은 삭제해 저장 공간을 절약한다.
- 또 다른 방식은 데이터를 장기 저장하기 위해 S3 등의 객체 스토리지 쓰는 것

### 17.9.2 대시보드를 위한 카파 아키텍처
![](files/Pasted%20image%2020260728221217.png)
- 각 판매 이벤트는 제품 ID와 시간 범위로 집계됨
- 이를 HDFS에 저장 후 배치하지 않는다.
	- 100만 제품 수는 단일 호스트에 쉽게 맞출 수 있지만 단일 호스트로 하루 10억 건 이벤트 처리는 어렵다
	- 다중 계층 집계가 필요하다
