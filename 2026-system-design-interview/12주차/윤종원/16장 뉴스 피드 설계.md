# 16. 뉴스 피드 설계
- 선택한 주제에 대해 시간 역순으로 정렬된 뉴스 항목 제공
- 뉴스 항목은 1 ~ 3개의 주제로 분류
- 사용자는 언제든지 최대 3개 주제 선택
- 사실 일반적인 피드 시스템

## 16.1 요구사항
- 사용자는 관심 주제를 선택할 수 있고, 최대 100개 태그
- 사용자는 한 번에 10개씩, 최대 1,000개까지 영어 뉴스 항목 목록을 가져올 수 있음
- 사용자는 최대 1,000개 항목 조회만 가능하지만, 시스템은 모든 항목 보관해야 함
- 지리적 위치와 관계없이 일단 제공하고, 이후에 개인화 고려할 수도 있다
- 최신 뉴스 먼저 보여준다. 역순 정렬되어야 하지만 근사치일 수 있다
- 구성 요소
	- 보통 여러 텍스트 필드 포함. 150자 제한 제목, 10,000자 제한 본문. 단순화를 위해 10,000자 제한 텍스트 필드 하나만 고려할 수도 있다
	- 항목이 생성된 시간을 나타내는 유닉스 타임스탬프
	- 오디오인지, 이미지인지, 동영상인지 고려 x. 시간이 있다면 최대 1MB의 0 ~ 10개의 이미지 파일 고려
	- 이미지를 제외하는 이유는 시스템이 상당히 복잡해지므로


- 다른 것들
	- 버전 관리 고려 x
	- 관심 주제, 표시된 기사, 읽기로 선택한 기사 등 추천 시스템 고려 x
	- 공유, 댓글, 개인화 등 기능 필요 x
	- 뉴스 항목 출처 고려 x. 그저 업로드 API만 제공
	- 검색 고려 X
	- 로그인, 결제, 구독, 수익화 고려x


- 비기능
	- 일일 활성 사용자 10만명이 각각 하루 평균 10회 요청, 100만 개의 뉴스 항목 처리 확장 가능
	- 읽기 P99 지연 1초 이내
	- 사용자 데이터 비공개
	- 최대 몇 시간 최종 일관성 허용. 몇 초 내에 가능하면 바람직. 실제 뉴스 서비스는 속보 항목을 따로 처리하기도
	- 쓰기 작업에는 고가용성 필요. 읽기는 개인 기기에 캐시되므로 필수는 아니다.

## 16.2 상위 수준 아키텍처
![](files/Pasted%20image%2020260722214649.png)

- 소스에서 뉴스 제출하면 DB에 기록된다
- 사용자는 피드 서비스에 쿼리하고, 이는 DB에서 가져와서 사용자에게 반환
- 이 아키텍처는
	- 수집 서비스는 고가용성 가지고, 무겁고 예측 불가능한 트래픽 처리해야 한다. 카프카 등을 고려한다
	- DB는 모든 항목을 보관하지만, 사용자에게는 최대 1,000개 항목만 제공.
		- 이는 모든 항목 보관 DB와 사용자에게 필요한 항목을 제공하는 DB를 분리할 수 있음을 시사한다
			- 각 사용 사례에 적합한 DB 기술을 선택할 수 있다.
		- 10,000자 -> UTF-8 기준 40KB
		- 1,000개 항목, 100개 태그 -> 약 1GB로 레디스에 쉽게 들어간다
		- 보관에는 HDFS 등 분산 샤딩 파일 시스템을 사용할 수도 있다
	- 최대 몇 시간의 최종 일관성 허용된다면 사용자 기기는 한 시간에 한 번 이상 뉴스 항목 업데이트할 필요가 없다. 피드 서비스의 부하를 줄일 수 있다.


![](files/Pasted%20image%2020260722214654.png)

- 피드 서비스의 출처는 새 게시물을 수집기로 푸시
- 수집기는 뉴스 항목만으로 수행할 수 있는 유효성 검사를 수행하고
- 다른 뉴스 항목이나 데이터에 의존하는 유효성 검사는 수행하지 않는다.
	- 예를 들면
		- SQL 인젝션 방어
		- 부적절한 언어 감지 필터링, 검열 작업 등 (즉시 거부와 수동 검토 등으로 나뉠 수도 있다)
		- 게시물이 차단된 출처에서 왔거나, 사용자에게 오지는 않았는지
		- 필수 필드 존재 여부
		- 최대 필드 길이 초과 여부
		- 구두점 등 금지 문자 포함하지는 않았는지


- 특정 출처의 요청은 수집기에 도달하기 전에 인증과 권한 부여 서비스를 통과해야 할 수 있다


- 예측 불가능한 트래픽 처리에는 카프카 등의 큐를 쓴다
- 소비자는 큐에서 폴링해 HDFS에 기록한다
- 최소한 두 개의 HDFS 테이블 필요하다
	- 원시 뉴스 항목
	- 사용자에게 제공할 준비가 된 뉴스 항목용
- 사용자에게 제공되기 전에 수동 검토가 필요한 항목을 위한 별도 테이블이 필요할 수도 있다


- 사용자가 포스트 조회를 요청하면
	- 메타데이터 서비스는 사용자의 태그 쿼리 후 백엔드 서비스를 통해 레디스 캐시에서 적절한 뉴스 항목을 쿼리한다
		- 두 서비스를 분리하는 이유는 필요한 사양이 다를 수도 있기 때문
		- 이렇게 하면 독립적으로 확장 가능
	- 레디스 캐시 키는 `(tag, hour)` 튜플이 될 수 있고, 값은 해당하는 뉴스 항목 목록이 될 수 있다.
	- 이 데이터 구조를 `{(tag, hour), [post]}`로 표현할 수 있다


- 최종 일관성 요구사항과 사용자는 한 시간에 한 번 이상 뉴스 항목을 업데이트할 필요가 없다면
- 요청 후 한 시간 이내에 업데이트를 요청할 시 두 가지 접근 중 하나를 택해 서비스 부하를 줄일 수 있다
	- 기기에서 요청 무시
	- 기기에서 요청하지만 응답이 504 초과면 재시도 X


![](files/Pasted%20image%2020260722214659.png)

- ETL 작업을 다른 카프카 큐에 기록한다 
- 백엔드 호스트가 사용자 요청 처리하지 않을 때 이를 소비해 레디스 테이블을 업데이트 할 수 있다
- ETL 작업은
	- 원시 뉴스 항목을 사용자에게 제공하기 전에 먼저 다른 뉴스 항목이나 외부 데이터와 연계된 유효성 검사, 검열
	- 중복 항목 찾기
	- 지난 1시간 이내에 제출할 수 있는 특정 태그, 주제에 대한 수 제한이 있는 경우 이에 대한 검사
- 이는 병렬로 수행하는 것도 가능하다.
- 결과적으로 각 검사를 통과한 ID들의 교집합을 HDFS에 저장하고, 이를 레디스에 복사해 덮어쓴다.


- 알림 서비스도 있을 거고, 이를 트리거하는 ETL도 있을 것

![](files/Pasted%20image%2020260722214704.png)

- 조정 기능도 핵심이다
	- 사용자를 차단한다거나 등
- 모든 조정 기능을 조정 서비스로 통합하는 것도 고려할 수 있다.
## 16.3 사전에 피드 준비하기
- 각 사용자는 `(tag, hour)` 쌍마다 레디스 쿼리가 필요하다
	- 경우에 따라 많은 쿼리가 필요하고, 이는 높은 트래픽과 높은 지연시간 유발할 수 있음
- 피드를 사전에 준비해서 저장 공간을 희생하고 낮은 지연시간과 트래픽을 얻을 수 있다
- `{user ID, post ID}`, `{post ID, post}` 두 개의 해시맵 준비
	- 후자와 달리 전자 해시맵은 유저 수에 비례하므로 꽤 커져 레디스 클러스터 용량을 초과할 수 있다
	- 해결책은 사용자를 지역별로 분할하고, 데이터 센터 당 두세 개의 지역만 저장하는 것
	- 혹은 샤딩된 SQL 구현을 쓰는 것
		- 사용자 ID가 노드 간 무작위로 분산되어 핫 샤드 문제를 방지할 수 있다.

![](files/Pasted%20image%2020260722214710.png)

![](files/Pasted%20image%2020260722214716.png)

- 백엔드는 어떻게 적절한 SQL 노드를 찾을 수 있나?
- 해싱된 사용자 ID를 클러스터 이름에 매핑해야 함
- 핫 샤드 감지하고, 클러스터 크기 조정해 트래픽 균형 맞추기 위해 트래픽 모니터링이 필요하다.
- 비용 절약을 위해 호스트의 하드디스크 용량 조정할 수도 있고, VM 크기 조정도 가능하다.

![](files/Pasted%20image%2020260722214722.png)

- 유일한 클라가 모바일 앱이라면 클라에 게시물 저장해 저장 공간을 절약할 수 있다
- 사용자가 게시물 한 번만 가져오고, 가져온 후에 해당 행 삭제한다고 가정할 수 있다.
- 사용자가 다른 모바일 기기로 로그인하면, 이전 기기에서 가져온 게시물을 볼 수 없게 된다.
- 이런 일은 충분히 드물게 발생하므로 수용 가능하다.
- 특히 뉴스는 빠르게 식상해지고, 사용자들이 게시물을 올린 지 며칠 후에는 거의 관심을 가지지 않기 때문이다.

![](files/Pasted%20image%2020260722214727.png)

- SQL 샤딩을 피하기 위해 두 접근 방식을 결합하는 것도 가능하다
- 모바일 앱을 열면 준비된 피드를 사용해 첫 번째 요청만 처리하고, 단일 노드에 맞는 수의 게시물 ID만 저장한다.
- 스크롤하면 더 많은 게시물을 요청하고, 이런 요청은 레디스에서 처리될 수 있다
- 이는 더 낮은 지연, 비용을 위해 더 높은 복잡성과 유지보수 부담을 트레이드오프한다.


- 클라가 레디스에서 동일한 게시물을 두 번 이상 가져오는 것을 피할 수 있는 몇 가지 방법을 논의해보자
	1. GET /post 요청에 게시물 ID를 포함해, 아직 가져오지 않은 게시물만 내려준다
	2. 레디스 테이블은 게시물을 시간별로 레이블링한다. 클라는 특정 시간의 게시물만 요청할 수 있다. 게시물이 너무 많으면 시간당 10분 단위 등 더 작은 시간으로 쪼갠다. 그 외 가능한 방법은 전체 게시물 ID 반환 API를 만들고, 사용자가 가져오고자 하는 게시물 ID를 지정할 수 있게 하는 것
## 16.4 검증과 콘텐츠 조정
![](files/Pasted%20image%2020260722214735.png)

- 검증으로 모든 문제를 막아낼 수 없고, 잘못 전달될 수 있다.
- 또 다른 접근 방식은 에어비앤비의 승인 방식
- 위 그림은 승인 서비스를 포함한 고수준 아키텍처를 보여준다
- 특정 ETL 작업은 수동 검토 플래그를 지정할 수도 있고, 이러한 게시물은 승인 서비스로 간다
- 승인되면 다시 사용자에게 전달된다.
### 16.4.1 사용자 기기의 게시물 변경
- 특정 유효성 검사는 자동화가 어렵다. 미완성된 기사라든지 등등
- 부적절한 단어 사용 등도 감지가 쉽지만 연령에 부적합한 내용, 폭탄 위협, 가짜 뉴스 등은 감지가 어렵다
- 시스템에서 모든 오류와 실패를 방지하려 해서는 안 된다. 이는 불가피하며, 이를 쉽게 감지하고 문제를 해결하며 수정할 수 있는 메커니즘을 개발해야 한다.
- 이상한 게시물이 실수로 사용자에게 전달될 수 있으며, 이를 삭제하거나 수정된 게시물로 덮어쓰는 기능이 필요하다.


- GET /post 엔드포인트를 수정할 수 있다.
- 사용자가 게시물을 가져올 때마다 응답에는 수정된 게시물 목록과 삭제할 게시물 목록이 포함되어야 한다.
- 클라 모바일 앱은 수정된 게시물을 표시하고, 적절한 게시물을 삭제해야 한다.


- 피드 서비스가 클라이언트 측 게시물을 수정하려면, 클라가 어떤 게시물을 가지고 있는지 파악할 수 있어야 한다
- 클라가 다운로드한 게시물 ID를 로그로 기록할 수는 있지만, 비용이 너무 크다.
- 다른 해결책은 GET /post 요청에 현재 게시물 ID 포함하는 것


### 16.4.2 게시물 태깅
- 검증에 실패한 게시물을 어떻게 해야 할까?
	- 삭제 -> 사용자 경험이 별로
	- 출처에 알리기 
	- 수동 검토 -> 대규모면 비용이 너무 커진다
- 교차 작업을 확장하면 검증이 실패했을 때 이를 출처에 알려 해결할 수 있다


- 또 다른 논의는 전 세계적으로 적용되는 규칙과 지역별 규칙을 구분해야 하는지 여부
- 혹은 사용자에 따라 일부 게시물을 필터링해야 할 수도 있다
- 사용자에게 특정 게시물을 필터링하기 위해 태그를 지정할 수 있다 (필터 태그, 필터)
	- 이는 회사가 제어하는 태그다.


- 이제 단일 레디스 조회만으로는 게시물을 내려줄 수 없고, 3개의 해시 테이블이 필요하다.
	- `{post ID, post}`: ID로 게시물 가져오기
	- `{tag, [post ID]}`: 태그로 게시물 ID 필터링
	- `{post ID, [filter]}`: 필터로 게시물 필터링


- 순서는 다음과 같다
	1. 메타데이터 서비스를 통해 클라 태그와 필터를 쿼리
	2. 이를 바탕으로 레디스를 쿼리해 게시물 ID를 얻는다
	3. 각 게시물 ID의 필터를 레디스에 쿼리하고 적절히 제외한다
	4. 각 게시물 ID로 레디스를 쿼리해 게시물을 가져오고, 이를 반환한다.


- 혹은 SQL로 한번에 가져오는 것도 가능하다.

```sql
SELECT post
FROM post p JOIN tag t ON p.post_id = t.post_id
LEFT JOIN filter f ON p.post_id = f.post_id
WHERE p.post_id IS NULL
```

- 지역별 뉴스 피드에서는 지역별로 레디스 캐시 분할하거나, 레디스 키에 추가 지역 열을 도입해야 할 수도 있다.

### 16.4.3 조정 서비스
- 여러 곳에서 검증이 일어난다
	- 클라
	- 수집기
	- ETL 작업
	- GET /post
- 이렇게 분산되면 유지보수가 어렵고 개발도 어렵다.
- 검증은 CPU 오버헤드지만, 이는 뉴스 피드 서비스의 트래픽을 줄이기도 한다.


- 서버 사이드 검증에 관해서는 수집기, ETL 작업, 백엔드가 기타 검증을 한다
- 이를 단일 서비스로 통합 -> 조정 서비스


- 조정 서비스의 일반적인 목적은 회사가 사용자가 제출한 게시물을 볼 수 있는지 제어하는 것
- 아래 기능 제공해야 한다
	- 검증 작업과 필터 구성
	- 게시물 변경하거나 삭제하는 조정 결정을 실행


- 조정을 단일 서비스로 통합하면 뉴스 피드 서비스 내의 다양한 서비스에서 작업하는 팀이 실수로 중복 검증을 구현하는 것을 방지하고, 콘텐츠 조정 팀의 비기술 직원이 엔지니어링 지원 없이 모든 조정 작업을 수행할 수 있다.

## 16.5 로깅, 모니터링, 경보
- 다음을 모니터링하고 경보
	- 특정 소스로부터 비정상적으로 많거나 적은 트래픽 비율
	- 모든 항목과 각 개별 소스 내에서 검증에 실패한 항목의 비정상적으로 높은 비율
	- 사용자가 기사를 악용이나 오류로 신고하는 등 부정적인 사용자 반응


- 파이프라인 전체에서 비정상적으로 긴 항목 처리 시간 등을 모니터링할 수도 있다

### 16.5.1 텍스트와 이미지 함께 제공
- 뉴스 항목에 최대 1MB 크기의 이미지 0~10개 허용하자
- 게시물 이미지를 게시물 객체의 일부로 여기고, 태그나 필터는 게시물 객체 전체에 적용된다고 보자
- 이는 GET /post 요청 부하를 크게 증가시킨다
	- 이미지 파일은 본문보다 크다. 다른 저장 기술을 고려할 수 있다
	- 이미지 파일은 여러 게시물에서 재사용될 수 있다
	- 이미지 파일 검증 알고리즘은 텍스트 검증과 다르다.

### 16.5.2 고수준 아키텍처
![](files/Pasted%20image%2020260723211653.png)
- 출처에서 미디어 업로드 사실을 알아야 하므로 동기식이어야 한다.
	- 이는 수집기 서비스의 클러스터가 훨씬 커져야 함을 의미한다

![](files/Pasted%20image%2020260723211657.png)

- 미디어 업로드는 메타데이터나 텍스트보다 더 많은 데이터 전송이 필요하므로 카프카 큐에 기사의 메타데이터와 텍스트를 생성하기 전에 미디어 업로드가 완료되어야 한다.
	- 미디어 업로드 성공했지만 메타데이터, 텍스트 생성에 실패하면 500을 반환할 수 있다
	- 이때 미디어 재업로드를 방지하기 위해 파일을 해싱하고, 이미 업로드되었는지 확인할 수 있다
	- 이를 통해 네트워크 비용을 줄일 수 있다


- 미디어 성공적으로 업로드했지만 카프카에 올리기 전에 수집기 호스트가 실패한다면?
- 미디어 업로드는 무거우니 삭제보단 유지하는 게 합리적이다
- 출처는 오류 응답을 받고 재시도할 수 있다.
- 주기적으로 감사 작업을 수행해 HDFS에 해당 메타데이터와 텍스트가 없는 미디어를 찾아 삭제할 수도 있다.

![](files/Pasted%20image%2020260724222527.png)

- 지리적으로 널리 분산되어 있거나 사용자 트래픽이 미디어 서비스에 너무 많은 부하를 준다면 CDN을 쓸 수도 있다.
- CDN 이미지 다운로드 인증 토큰은 API Gateway에서 부여할 수 있다.
- 기사 텍스트, 미디어 URL은 레디스가 주고
- 이미지는 CDN이 준다.


- 미디어 서비스와 CDN 동시에 쓰는 이유는 일부 기사를 사용자에게 제공하지 않아 일부 이미지를 CDN에 저장할 필요가 없어 비용을 줄일 수 있다
- 또한 기사가 자동 승인되면 기사의 미디어를 CDN에 업로드해야 하고, 이 또한 미디어 서비스가 처리할 수 있다.


- 텍스트와 미디어를 별도의 서비스에서 처리하고 저장하는 것과 단일 서비스에서 처리하고 저장하는 것의 트레이드오프를 논의할 수도 있다


- 텍스트와 미디어 전체를 CDN에 호스팅할 수도 있다
- 레디스 값은 기사 ID로 축소될 수 있다
- 기사 텍스트 양은 작지만, 요청이 빈번한 기사는 CDN으로 성능 향상을 얻을 수도 있다
- 레디스는 수평적으로 확장 가능하지만 데이터 센터 간 복제는 복잡하다.


- 미디어를 어떻게 더 효율적으로 검토할 수 있을까?
- 매번 오디오를 다 듣거나 비디오를 다 보는 건 비효율적이다.
- 오디오를 문자화해서 읽게하는 것도 좋은 방법이다.
- 혹은 머신러닝 솔루션을 도입할 수도 있다.

## 16.6 기타 논의 가능한 주제
- 고정된 주제 집합 대신 동적인 해시 태그
- 사용자가 다른 사용자나 그룹과 뉴스 공유
- 알림 전송
- 실시간 배포 ETL -> 스트리밍
- 속보 등 특정 기사를 다른 기사보다 우선시


- 기능 요구사항이 아닌 것
	- 분석
	- 개인화
	- 영어 외의 다른 언어 기사 제공
	- 뉴스 피드 수익화
		- 구독 시스템
		- 특정 게시물을 구독자용으로 예약
		- 비구독자를 위한 기사 제한
		- 광고와 프로모션 게시물
