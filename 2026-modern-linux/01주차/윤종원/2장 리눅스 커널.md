# 2장 리눅스 커널

## 리눅스 아키텍처
![](files/Pasted%20image%2020260809210702.png)
- 하드웨어 계층
	- CPU, 메모리, 디스크, 네트워크 인터페이스, 키보드 모니터 등등
- 커널 계층
	- 커널과 사용자 영역 사이에는 init 시스템과 시스템 서비스 등 다양한 구성요소가 있지만 엄밀히는 커널의 일부가 아니다
- 사용자 영역 계층
	- 셸, ps, ssh 등의 유틸리티, GUI 등 앱이 실행되는 곳


- 다른 계층 간의 인터페이스는 리눅스 운영체제 패키지의 일부이다. -> system call 이라는 인터페이스
- 하드웨어와 커널 사이의 인터페이스는 시스템 콜과 달리 단일 인터페이스가 아니라 하드웨어별로 그룹화된 개별 인터페이스 모음으로 구성된다.
	- CPU 인터페이스
	- 메모리 인터페이스
	- 네트워크 인터페이스, 드라이버
	- 파일 시스템과 블록 디바이스 드라이버 인터페이스
	- 캐릭터 디바이스, 하드웨어 인터럽트, 키보드, 터미널, 기타 I/O 등의 입력 디바이스를 위한 디바이스 드라이버


- 사용자 모드, 커널 모드는 실질적으로 하드웨어 접근 권한이 얼마나 있고 사용 가능한 추상화가 얼마나 제한되었는지를 나타낸다.
- 커널 모드는 추상화를 제한해 빠르게 실행하지만
- 유저 모드는 상대적으로 느리지만 더 안전하고 편리한 추상화를 의미한다.

## CPU 아키텍처
- 리눅스 커널은 아키텍처별 코드도 포함하고 있다
- 이런 분리 덕분에 리눅스를 새 하드웨어에 이식하고 빠르게 사용하는 것이 가능하다.


- BIOS와 UEFI
	- 유닉스와 리눅스는 전통적으로 자체 부트스트랩을 위해 BIOS를 사용한다.
	- 하드웨어는 BIOS의 일부인 POST(Power On Self Test)를 실행하도록 연결된다.
	- POST는 하드웨어가 지정된 대로 동작하는지 확인한다.
	- 모던 환경에서는 이런 BIOS 기능이 운영체제와 플랫폼 펌웨어 간의 소프트웨어 인터페이스를 정의하는 UEFI로 대체되었다.
	- 그러나 여전히 여러 곳에서 BIOS라는 용어를 접할 수 있으며, 이는 사실 UEFI다.


- 어떻게 리눅스를 실행 중인 CPU를 파악할 수 있을까?
- 한 가지 방법은 BIOS와 상호작용하는 `dmidecode`라는 전용 도구를 쓰는 것
- 혹은 `cat /proc/cpuinfo`, `uname -m` 등도 가능하다.

### x86 아키텍처
- 강력하고 널리 사용 가능하지만 에너지 효율이 좋지는 않다
- 부분적으로 비순차적 실행해 최적화를 많이 해 멜트다운 등 보안 문제 등이 있었다

### ARM 아키텍처
- RISC
- 일반적으로 더 빠르게 실행할 수 있는 작은 명령어 세트와 많은 일반 CPU 레지스터로 구성
- 빠르고 저렴하고 발열량이 적어 데이터 센터에 많아지고 있다.

### RISC-V 아키텍처
- 원래는 UC버클리에서 개발한 개방형 RISC 표준
- 아직 널리 사용되지 않는 CPU 제품군

## 커널 구성요소
- 리눅스 커널은 모놀리식 커널 (모든 구성요소가 단일 바이너리 일부)
- 코드 베이스에서는 특정 역할을 식별하고 부여할 수 있는 기능 영역이 나뉘어 있음
	- 프로세스 관리
		- 실행 파일을 기반으로 프로세스 시작
	- 메모리 관리
		- 프로세스에 메모리 할당하거나 파일을 메모리에 매핑
	- 네트워킹
		- 네트워크 인터페이스 관리나 네트워크 스택 제공
	- 파일 시스템
		- 파일 관리 제공하고, 파일 생성 삭제 지원 
	- 캐릭터 디바이스와 디바이스 드라이버 관리
- 이런 구성 요소는 상호 의존성이 많아 커널의 개발자 모토인 '커널은 사용자 영역을 손상시키지 않는다'를 지키며 작업하기는 정말 어렵다.

### 프로세스 관리
- 일부는 인터럽트 등을 처리하고 일부는 프로그램 실행과 스케줄링에 중점을 둔다.
- 일반적으로 프로세스는 실행 가능한 프로그램을 기반으로 하며, 사용자가 대면하는 유닛이다
- 스레드는 프로세스 컨텍스트 상에서의 실행 유닛을 말한다.
- 즉, 프로세스에는 여러 실행 유닛이 병렬로 실행되며 이는 잠재적으로 각기 다른 CPU에서 실행될 수 있다.


- 세션
	- 하나 이상의 프로세스 그룹을 포함하고, 선택적으로 tty가 연결된 상위 수준의 사용자 대면 유닛
	- 커널은 세션 ID(SID)로 세션을 식별
- 프로세스 그룹
	- 하나 이상의 프로세스가 포함
	- 한 세션에는 foreground 프로세스 그룹이 둘일 수 없다
	- 커널은 프로세스 그룹 ID(PGID)라는 숫자로 이를 식별
- 프로세스
	- 여러 리소스(주소 공간, 스레드, 소켓 등)을 그룹으로 추상화한 것
	- 커널은 `/proc/self`를 통해 현재 프로세스를 사용자에게 노출
	- 커널은 프로세스 ID(PID)로 식별
- 스레드
	- 커널에 의해 프로세스로 구현된 유닛
	- 스레드를 나타내는 전용 데이터 구조는 없다
	- 오히려 스레드는 특정 리소스를 다른 프로세스와 공유한다
	- 커널은 스레드 ID(TID)와 스레드 그룹 ID(TGID)로 식별
	- 공유된 TGID 값은 멀티스레드 프로세스를 의미
- 태스크
	- `sched.h`에 정의된 `task_struct`라는 데이터 구조가 있고, 이는 프로세스와 스레드 구현의 기반을 형성
	- 이 데이터 구조는 스케줄링 관련 정보, 식별자, 시그널 처리기, 성능이나 보안과 관련된 기타 정보를 수집
	- 모든 유닛은 태스크에서 파생되며 고정(anchor)된다.
	- 그러나 태스크는 커널 외부에 그대로 노출될 일이 없다.


- `ps -j`로 값을 확인할 수 있다.

### 메모리 관리
![](files/Pasted%20image%2020260809214341.png)

- 가상 메모리는 시스템이 물리적으로 갖고 있는 것보다 더 많은 메모리를 갖고 있는 것처럼 보이게 한다
- 사실 모든 프로세스는 많은 (가상) 메모리를 얻는다
- 물리 메모리와 가상 메모리 모두 페이지라고 부르는 고정 길이 청크로 나눈다.


- 각 프로세스 수준의 페이지 테이블을 통해 여러 가상 페이지가 동일한 물리적 페이지를 가리킬 수 있다
- CPU가 프로세스의 가상 페이지에 접근할 때마다 원칙적으로 CPU는 프로세스가 사용하는 가상 주소를 이에 해당하는 물리 주소로 변환해야 함
- 최신 CPU 아키텍처는 TLB(Translation Lookaside Buffer)라는 조회용 온칩을 지원
	- 매우 작은 캐시.


- 전통적으로 리눅스 기본 페이지 크기는 4KB였지만 커널 v2.6.3부터는 대형 페이지도 지원


- `/proc/meminfo`는 사용 가능한 RAM 양처럼 메모리 관련 정보 파악할 때 매우 유용

### 네트워킹
- 리눅스 네트워크 스택은 계층화된 아키텍처를 따른다
	- 소켓
	- TCP, UDP
	- IP

### 파일시스템
- 파일 시스템 써서 HDD, SSD 등의 파일과 디렉터리 구성
- ext4, btrfs, NTFS 등 다양한 파일 시스템 존재
- VFS는 여러 파일 시스템 유형과 인스턴스 지원하기위해 도입되었다
- VFS의 최상위 계층은 열기, 닫기, 읽기, 쓰기 등 공통 API 추상화를 제공하며, VFS 최하위 계층은 주어진 파일 시스템에 대한 **플러그인**이라 불리는 파일 시스템 추상화다.

### 디바이스 드라이버
- 드라이버는 커널에서 실행되는 코드다
- 키보드, 마우스, HDD 등 실제 하드웨어 디바이스나 `/dev/pts/` 아래의 의사 터미널 같은 의사 디바이스를 관리한다.
- 드라이버는 커널에 정적 빌드될 수도 있고, 필요할 때 동적 로드될 수 있도록 커널 모듈로 빌드될 수도 있다.

### 시스템 콜
- 파일 생성을 하든 다운로드를 하든 결국 상위 수준의 명령을 일련의 구체적인 아키텍처 종속 단계로 전환하도록 리눅스에게 요청하게 된다
- 다시 말해, 커널이 노출하는 서비스 인터페이스와 해당 사용자 영역의 엔티티 호출은 시스템 호출의 모음이라 하며, 이를 **시스템 콜**이라 부른다.


- 일반적으로 직접 시스템 콜을 호출하지 않고, C 표준 라이브러리 등 추상화된 라이브러리를 통해 호출한다.
- 표준 라이브러리는 래퍼 기능을 제공하며, glibc, musl 등 다양한 구현체에서 사용할 수 있다.

![](files/Pasted%20image%2020260811213034.png)

- 래퍼 라이브러리는 시스템 콜 실행의 반복적인 저수준 처리를 다룬다.
	1. `syscall.h`와 아키텍처 종속 파일에 정의되어 메모리에 있는 함수 포인터 배열을 통해서 시스템 콜과 해당 핸들러를 추적한다.
	2. 시스템 콜 멀티플렉서처럼 동작하는 `system_call()` 함수를 사용해 먼저 하드웨어 컨텍스트를 스택에 저장하고, 검사를 수행하고, 그 이후에 `sys_call_table`의 각 시스템 콜 번호의 인덱스가 가리키는 함수로 점프한다.
	3. `sysexit`로 시스템 콜이 완료되면 래퍼 라이브러리는 하드웨어 컨텍스트 복원 후 프로그램 실행은 다시 사용자 영역에서 시작된다.
- 여기서 시간이 많이 소요되는 건 커널 영역과 사용자 영역 모드 간 전환



- `strace`를 사용하면 특정 명령이 어떤 시스템 콜을 사용하는지 추적할 수 있다.
	- 사용자 영역과 커널 사이에 이벤트 라이브 스트림을 가로채는 방식으로 이를 파악한다.
	- 어떤 시스템 호출이 어떤 순서로 어떤 인수를 사용해 호출했는지 정확하게 파악하기 위해 유용하다.

- 최신 리눅스는 하드웨어 자동 감지해 모듈을 자동 로딩하지만 원하면 수동으로 로드할 수도 있다

### 커널을 확장하는 현대적인 방법: eBPF
- 커널을 확장하는 방법으로 더 인기를 끌고 있는 것은 eBPF다. 원래는 BPF(Berkeley Packet Filter)라 불렸으며, 최근에는 eBPF로 불린다.


- eBPF는 리눅스 커널 기능으로, 3.15 이상이 필요하다
- `bpf` 시스템 콜 사용해서 커널 기능을 안전하고 효율적으로 확장 가능하다.
- 이는 맞춤형 64비트 RISC 명령어 세트를 사용한 커널 내 가상 머신으로 구현되었다.

![](files/Pasted%20image%2020260811214218.png)

- 이는 여러 사례에서 이미 사용되고 있다
	- Pod networking을 위한 CNI 플러그인 (Cilium, Calico 등)
	- bpftrace, hubble 등 커널 추적 및 클러스터 설정
	- CNCF Falco 등 보안 제어
	- 페이스북의 L4 Katran 등 로드밸런서
