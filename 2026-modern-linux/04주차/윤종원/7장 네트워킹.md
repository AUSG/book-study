# 7장 네트워킹

## 기본 개요
- 네트워크는 변화하는 분야이고, 계층이 많아 문제가 발생하면 어디가 정확히 문제인지 파악이 어렵다
- 또한 여러 추상화가 존재해 문제 해결을 방해한다.

## TCP/IP 스택
![](files/Pasted%20image%2020260907224850.png)
- 링크 계층
	- 하드웨어와 커널 드라이버를 다루며 물리적 디바이스 간에 패킷이 어떻게 전송되는지를 다룬다.
- 인터넷 계층
	- IP 사용해 라우팅 다룬다
	- 네트워크를 통한 기기 간의 패킷 전송 지원
- 전송 계층
	- 세션 기반의 안정적인 통신을 위한 TCP, UDP 사용해 호스트 사이의 종단 간 통신 제어
	- 패킷 전송 방식을 다루고, 포트를 통한 시스템의 개별 서비스 지정과 데이터 무결성 다룸
	- 리눅스는 소켓을 통신의 엔드포인트로 지원
- 애플리케이션 계층
	- 웹, SSH, 메일 등 사용자 대면 도구와 앱을 다룬다
### 링크 계층
- 바이트, 유선, 전자기파, 디바이스 드라이버, 네트워크 인터페이스 등 하드웨어와 관련된 것들
- 이더넷
	- 유선을 사용해 기기 연결. LAN 등
- 무선
	- Wi-Fi 등으로 전자기파 사용해 통신
- MAC 주소
	- media access control
	- 각 하드웨어마다 고유한 48비트 식별자. 각 기기를 식별
	- 첫 24비트 조직 고유 식별자로 사용
- 인터페이스
	- 네트워크 연결.
	- 물리적 인터페이스일 수도 루프백 인터페이스 `lo` 등의 가상 인터페이스일 수도 있다

- 전송하려는 바이트의 디지털 표현 <-> 전기 혹은 전자기 신호
- NIC 정보를 알기 위해서는 `ifconfig`나 `ip` 사용

### 인터넷 계층
- 네트워크의 한 시스템에서 다른 시스템으로 라우팅
- 인터넷 계층의 설계는 사용 가능한 네트워크 인프라가 신뢰할 수 없고 참여자가 자주 변경된다고 가정
- 최선의 전달(성능 보장 X)을 제공하고 모든 패킷을 독립적으로 취급
- 그 상위 계층이 패킷 순서, 재시도, 배달 보장 등을 처리
- 기기를 논리적으로 고유하게 식별하기 위해 IP를 쓴다.

#### IPv4
- TCP/IP 통신에서 엔드포인트 역할을 하는 호스트나 프로세스를 고유하게 식별하는 32비트 숫자 정의
- RFC 791 등 IETF 사양에 정의된 것처럼, IP 헤더에는 많은 필드가 있지만 알아야 하는 필드는 다음과 같다.
![](files/Pasted%20image%2020260907225705.png)
- source address(32비트) : 송신자 IP 주소 
- destination address(32비트) : 수신자 IP 주소
- 프로토콜(8비트) : RFC 790에 나온 페이로드 유형 (TCP, UDP, ICMP 등)
- TTL(8비트)
- ToS(8비트) : QoS 용도로 사용

- 오늘날에는 CIDR이 IP 주소 할당과 관련된 유일한 방법
	- `10.0.0.0/24`
	- 이 경우 넷마스크는 `255.255.255.0`
- 예약된 IPv4 주소
	- 127.0.0.0
		- 로컬 주소용 예약. 127.0.0.1은 루프백 주소
	- 169.254.0.0/16
		- 링크 로컬 주소로 전송된 패킷이 네트워크의 다른 부분으로 전달되지 않아야 함을 의미
		- AWS 등은 이를 특수 서비스에 사용 (메타데이터)
	- 224.0.0.0/24
		- 멀티캐스트 예약됨
- RFC 1918에는 사설 IP 범위 정의되어 있다.
	- 10/8, 172.16/12, 192.168/16
- `0.0.0.0`은 라우팅 불가능한 주소이며 상황에 따라 사용 사례와 의미가 다르지만 서버 관점에서는 모든 IPv4 주소를 의미한다.
- 알려진 IP로 바뀔 때까지 송신지 선택을 위해 모든 사용 가능한 IP 주소에서 수신 대기하라는 의미.

![](files/Pasted%20image%2020260907230043.png)

#### IPv6
- TCP/IP 통신에서 엔드포인트 식별용으로 쓰이는 128비트 숫자
- 개별 기기를 10^38개 할당 가능
- IPv4와 달리 16비트로 구성된 8개 그룹을 `:`으로 구분하는 16진수 표현식 사용


- 축약형이 있다
	- 선행되는 0을 제거하거나 연속되는 0의 섹션을 압축해 `::`로 대체
	- IPv6의 루프백 주소는 `::1`
- IPv4처럼 예약 주소도 있다.


- IPv4와 호환되지 않는다.
- 즉, 휴대폰 같은 종단 디바이스에서 라우터, 서버, 소프트웨어 등 모두 IPv6 지원해야 한다.

#### 인터넷 제어 메시지 프로토콜
- RFC 792에는 에러 메시지와 가용성 등 운영 정보를 보내는 저수준 구성요소에 사용되는 Internet Control Message Protocol(ICMP)가 있다.
![](files/Pasted%20image%2020260907230409.png)

#### 라우팅
- 라우팅 테이블 조작에는 `iptables`가 쓰인다. 패킷을 가로채고 조작하기 위해 `netfilter`를 쓴다.
![](files/Pasted%20image%2020260907230442.png)
- 이보다 현대적인 방법은 `ip`를 쓰는 것
![](files/Pasted%20image%2020260907230459.png)
- 인터넷이 끊겼다면 `traceroute`를 쓸 수도 있다.
![](files/Pasted%20image%2020260907230511.png)


- RFC 4271과 기타 IETF 사양에 정의된 BGP
- BGP와 직접 상호작용할 가능성은 낮지만 존재를 인식하고 수행하는 작업의 핵심을 이해하는 것은 중요하다.


- BGP 용어로 네트워크는 AS(Autonomous System)라고 부른다
- IP 라우팅이 동작하려면 이런 자율 시스템들이 해당 라우팅 데이터와 도달 가능성 데이터를 공유하고 인터넷을 통해 패킷 전달 경로를 알려야 한다.

### 전송 계층
#### 포트
- 어떤 프로토콜이 사용되든 그 각각은 포트가 필요하다
- 포트란 IP 주소에서 사용 가능한 서비스를 식별하는 고유한 16비트 숫자
	- 잘 알려진 포트 (0 ~ 1023)
		- SSH, 웹 서버 등
		- 이들 중 하나를 사용하려면 높은 권한 필요
	- 등록된 포트 (1024 ~ 49151)
		- IANA가 공개적으로 문서화된 프로세스를 통해 관리
	- 한시적 포트 (49152 ~ 65535)
		- 등록할 수 없는 포트. 한시적 포트를 자동으로 할당하는 데 사용되거나 개인 서비스에도 사용될 수 있음
- `/etc/services`에서 포트와 매핑을 볼 수 있다.
![](files/Pasted%20image%2020260907230807.png)

#### 전송 제어 프로토콜
- Transmission Control Protocol
- HTTP, SSH 등 여러 고수준 프로토콜에서 쓰이는 연결 지향 전송 계층 프로토콜
- 패킷 순서대로 전달 보장하고, 오류 발생 시 재전송 지원하는 세션 기반 프로토콜
- RFC 793 및 관련된 IETF 사양에 정의된 TCP 헤더에서는 다음 필드가 중요하다.
![](files/Pasted%20image%2020260907231109.png)
- 송신자 포트(16비트)
- 수신자 포트(16비트)
- 시퀀스 번호(32비트) : 순차 배송 관리
- ACK (32비트) : ack, SYN, ACK 플래그는 TCP/IP 3-way handshake 의 핵심
- 플래그(9비트) : SYN, ACK가 제일 중요
- 윈도우(16비트) : 수신창 크기
- 체크섬(16비트) : 오류 검사에 쓰임


- TCP는 연결 수립부터 종료까지 연결 상태를 추적하며 송신자, 수신자 모두 전송할 데이터 양(윈도우 크기)부터 QoS까지 협상해야 한다.
- 보안 관점에서 TCP에는 방어 메커니즘이 없다. 즉, 페이로드는 일반 텍스트로 전송된다.
- 메시지 암호화를 활성화하려면 TLS 프로토콜을 사용해야 한다.

#### 사용자 데이터그램 프로토콜
- User Datagram Protocol
- 통신 설정 없이 데이터그램이라고 부르는 메시지를 보낼 수 있는 비연결형 전송 계층 프로토콜
- 무결성 보장을 위해 체크섬은 지원
- 오버헤드가 거의 없고 높은 처리량 달성 가능
- NTP, DHCP, DNS 등에 많이 쓰인다.
- RFC 768에 따라 중요한 필드는 다음과 같다.
![](files/Pasted%20image%2020260907231333.png)
- 송신자 포트(16비트)
- 수신자 포트(16비트)
- 길이(16비트) : UDP 헤더 + 데이터 총 길이
- 체크섬(16비트) : 에러 확인을 위해 선택적으로 사용

## DNS
- 과거에는 이름과 IP 주소 간 매핑을 `/etc/hosts`로 유지
- Network Information Center(NIC)는 FTP를 통해 `HOSTS.txt` 파일을 모든 참여 호스트와 공유
- 그러나 이런 방식은 한계가 있기에 분산 시스템이 설계됨


- DNS와 관련된 RFC가 많지만, 원본인 RFC 1034와 구현 지침인 RFC 1035는 여전히 유효하다.
- 주요 개념
	- domain name space
		- `.`가 루트인 트리 구조로 각 트리 노드와 리프에는 특정 공간에 대한 정보가 포함되어 있다
		- 리프에서 루트까지의 경로인 레이블(최대 63바이트)을 정규화된 도메인 네임(fully qualified domain name, FQDN)이라고 부른다.
		- `demo.mhausenblas.info.`는 최상위 도메인이 `.info`인 FQDN. 보통 맨 오른쪽 마침표는 생략
	- resource record
		- 도메인 네임 스페이스의 노드나 리프에 있는 페이로드
	- name server
		- 도메인 트리 구조 정보를 가지고 있는 서버 프로그램
		- 네임 서버가 네임스페이스에 대한 완전한 정보를 가지고 있는 경우 authoritative name server라고 한다.
		- 권위 있는 정보는 `zone`으로 구성된다.
	- resolver
		- 클라 요청에 응답으로 네임 서버에서 정보를 추출하는 프로그램
		- 로컬에 있는 시스템이며 리졸버와 클라 간의 상호작용을 위해 정의된 명시적인 프로토콜은 없다
![](files/Pasted%20image%2020260907232230.png)
- DNS는 계층 네이밍 시스템이며 루트에는 최상위 도메인의 레코드를 관리하는 13개의 루트 서버가 있다.
- 루트 바로 아래에는 최상위 도메인(top-level domain, TLD)가 있다.
	- 인프라 최상위 도메인
		- IANA가 IETF 대신해 관리하며 example과 localhost 등을 포함
	- 일반 최상위 도메인(gTLD)
		- .org, .com 등 3개 이상의 문자가 포함된 일반 도메인
	- 국가 코드 최상위 도메인(ccTLD)
		- 두 글자로 된 ISO 국가 코드가 할당된 국가나 지역을 위한 도메인
	- 스폰서 최상위 도메인(sTLD)
		- .aero, .gov 등 TLD를 사용할 수 있는 자격을 제한하는 규칙을 세우고 시행하는 민간 기관이나 조직을 위한 도메인

### DNS 레코드
- 네임 서버는 유형이나 페이로드를 비롯해 그 밖의 필드를 캡처하는 레코드 관리
- TTL 등도 포함
- FQDN을 노드의 주소로, 리소스 레코드를 노드의 데이터인 페이로드로 생각할 수 있다.
- 다양한 레코드 유형
	- A 레코드(RFC 1035), AAAA 레코드(RFC 3596)
		- 각각 IPv4, IPv6 주소 레코드
		- 일반적으로 호스트 이름을 IP 주소에 매핑하는 데 쓴다
	- CNAME 레코드(RFC 1035)
		- 한 이름의 Alias를 다른 이름에 제공하는 Canonical name 레코드다
	- NS 레코드(RFC 1035)
		- 권위 있는 네임 서버 사용하도록 DNS 존을 위임하는 네임 서버 레코드
	- PTR 레코드(RFC 1035)
		- 역방향 DNS 조회 수행하는 데 쓰이는 포인터 레코드. A 레코드의 반대
	- SRV 레코드(RFC 2782)
		- 서비스 로케이터 레코드. 일반적인 탐색 메커니즘이라 할 수 있다
	- TXT 레코드 (RFC 1035)
		- 텍스트 레코드. 원래는 사람이 읽기 위한 용도였지만 지금은 보안 관점에서 기계가 판독할 수 있는 데이터를 넣는 경우가 많다.
- 또한 존재하지 않는 모든 이름에 대한 요청을 매칭하기 위한 `*`로 시작하는 와일드카드 레코드도 있다.
	- `*.mhausenblas.info`


- DNS 레코드는 바인드와 같이 네임 서버가 읽고 데이터베이스의 일부로 생성하는 zone 파일에 텍스트 형식으로 표시된다.

### DNS 조회
![](files/Pasted%20image%2020260909200257.png)
- `host` 명령으로 로컬 네임을 쿼리해서 IP 주소를 확인하거나 반대로 IP 주소 쿼리해서 도메인 네임을 확인할 수 있다.
- `dig`로 더 자세히 조회할 수 있다.

![](files/Pasted%20image%2020260909200616.png)
- 혹은 `dog`, `nslookup`


- SRV 레코드 유형은 일반적인 탐색 메커니즘 역할을 한다
- IETF 커뮤니티에서는 RFC에 새 서비스에 대한 새 레코드 유형을 매번 정의하는 대신 향후 나올 서비스 유형을 처리할 수 있는 일반적인 방법을 정의했다.
- SRV 레코드로 DNS를 통해 서비스의 IP 주소와 포트와 통신하는 방법을 설명한다.
![](files/Pasted%20image%2020260909200722.png)
- XMPP 서비스가 사용 가능한지 알고 싶다면 위와 같은 방법으로 정보를 얻을 수 있다.
