# 6장 애플리케이션, 패키지 관리, 컨테이너

## 기본 개요
- 프로그램
	- 메모리에 로드하고 실행할 수 있는 바이너리 파일 혹은 셸 스크립트
	- 또 다른 이름은 실행 파일(`executable`)
	- 실행 파일 유형에 따라 누가 그걸 관리하는지 정해진다.
	- 예를 들어 셸 스크립트는 셸이 해석하고 실행한다
- 프로세스
	- 프로그램 기반의 실행 엔티티
	- 슬립 상태가 아닌 한 메인 메모리에 로드되어 CPU, I/O 사용
- 데몬
	- 데몬 프로세스의 줄임말로 서비스라고도 한다
	- 다른 프로세스에 특정 기능을 제공하는 백그라운드 프로세스
	- 프린터 데몬을 사용하면 인쇄가 가능해진다
- 애플리케이션
	- 종속성을 포함한 프로그램
	- 사용자 인터페이스를 포함한 실질적인 프로그램
	- 검색, 업그레이드를 위한 설치, 제거 등 모든 수명주기, 구성, 데이터와 연관해 애플리케이션이라는 용어를 사용한다
- 패키지
	- 프로그램과 구성을 포함한 파일
	- 소프트웨어 애플리케이션 배포에 사용
- 패키지 관리자
	- 패키지를 입력값으로 받아 해당 콘텐츠와 지침에 따라 리눅스 환경에 패키지를 설치, 업그레이드, 제거하는 프로그램
- 공급망
	- 패키지를 기반으로 사용자가 애플리케이션을 찾고, 사용할 수 있는 소프트웨어 생산자와 배포자의 모음
- 부팅
	- 리눅스를 사용할 수 있는 상태로 만드는 것을 목표로 하드웨어와 OS를 초기화하는 리눅스의 시작 시퀀스
	- 커널 로딩과 서비스 프로그램 시작도 포함된다

## 리눅스 시작 프로세스
![](files/Pasted%20image%2020260830204955.png)
1. 모던 환경에서 통일 확장 펌웨어 인터페이스(UEFI) 사양은 부팅 구성(NVRAM에 저장됨)과 부팅 로더를 정의. 이전 시스템에서는 POST가 완료되면 기본 I/O 시스템이 하드웨어 초기화하고 부트 로더에게 제어권 넘긴다
2. 부트 로더의 목표는 커널을 부트스트랩하는 것
3. 커널은 일반적으로 압축된 형태로 `/boot`에 있다. 이를 추출해 메인 메모리에 로드 후 하위 시스템, 파일 시스템, 드라이버 등을 초기화하면 init 시스템에 제어권을 넘기고 부팅 프로세스는 종료된다
4. init 시스템은 시스템 전반에 걸쳐 데몬을 실행할 책임이 있다. 프로세스 계층 구조의 루트(PID 1)이며, 시스템 전원 끌 때까지 실행된다. PID 1은 고아 프로세스도 처리한다
5. 환경에 따라 사용자 공간 수준의 초기화 진행
	- 터미널, 환경, 셸 초기화
	- GUI가 있는 경우 이와 관련된 초기화

- 시스템 V 스타일의 init 시스템은 리눅스 전통적인 init 시스템이었음
- 유닉스로부터 Sys V 물려받았는데, 이는 소위 런레벨을 정의하고 구성 파일은 보통 `/etc/init.d`에 저장되어 있다
- 그러나 데몬을 순차적으로 시작하는 방식과 배포판 구성별로 다르게 처리해야 한다는 점 때문에 이식성이 떨어짐

## systemd
- 처음에는 initd를 대체하는 init 시스템
- 최근에는 로깅, 네트워크 구성, 네트워크 시간 동기화 등을 포함하는 관리자
- 데몬과 해당 종속성을 정의하는 유연하고 이식 가능한 방법은 물론 구성을 제어하는 통일된 인터페이스도 제공


- 아래 특징
	- 여러 배포판에서 리눅스의 시작을 관리할 수 있는 통일된 방법 제공
	- 빠르고 이해하기 쉬운 서비스 구성 구현
	- 모니터링, 리소스 사용 제어, 내장된 감사 기능을 포함한 최신 관리 제품군 제공
- 또한 init은 초기화 때 순서대로 서비스를 시작하지만 systemd는 어느 서비스든 종속성만 충족되면 시작할 수 있어 시작 시간을 단축할 수 있는 잠재력이 있다

### 유닛
- 기능 및 대상 리소스에 따라 의미 체계가 다른 논리 그룹
- 대상 리소스에 따라 여러 유닛을 구분

- service 유닛 : 서비스나 애플리케이션 관리 방법 설명
- target 유닛 : 종속성
- mount 유닛 : 마운트 지점 정의
- timer 유닛 : 크론 작업 등 정의

- 중요도가 낮은 유닛 유형
	- socket : 네트워크나 IPC 소켓
	- device : udev, sysfs 파일시스템용
	- automount : 자동 마운트 지점
	- swap : 스왑 공간
	- path : 경로 기반 활성화
	- snapshot : 변경사항이 일어난 후 현재 상태 재구성
	- slice : cgroup과 엮임
	- scope : 외부에서 생성된 시스템 프로세스 세트 관리

- systemd에 인식되려면 유닛은 한 파일로 직렬화되어야 함
- 여러 위치에서 찾는데 중요한 경로는 3개
	- /lib/systemd/system : 패키지가 설치한 유닛
	- /etc/systemd/system : 시스템 관리자가 구성한 유닛 
	- /run/systemd/system : 비지속적인 런타임 수정사항

## 리눅스 애플리케이션 공급망
![](files/Pasted%20image%2020260830211150.png)
- 공급망(supply chain)이란 소비자에게 제품을 공급하는 조직이나 개인들의 시스템

- 소프트웨어 유지 보수 담당자
	- 소프트웨어 아티팩트 생성해 올리는 개별 개발자
	- 오픈소스 프로젝트, ISV 등이 포함
- 저장소
	- 앱의 일부 혹은 전체가 메타데이터와 함께 포함된 패키지가 있다
	- 패키지는 앱의 종속성도 캡처
- 도구(패키지 관리자)
	- 패키지 관리자를 사용해 저장소에 위치한 패키지 조회하고, 설치하고, 업데이트하고, 삭제할 수 있다

![](files/Pasted%20image%2020260830211323.png)
- 전통적인 패키지 관리자
	- 이 카테고리에서는 저수준 도구와 고수준 도구를 구분
	- 패키지 관리자가 종속성을 해결할 수 있고 고수준 인터페이스를 제공하면 고수준 패키지 관리자라 부른다
- 컨테이너 기반 솔루션
	- 처음에는 서버, 클라우드 컴퓨팅 영역에서 나온 솔루션
	- 애플리케이션 관리에 사용하기 좋다
- 최신 패키지 관리자
	- 데스크톱 환경에 뿌리를 두었다
	- 사용자가 앱을 최대한 쉽게 사용하게 하는 것

## 패키지와 패키지 관리자
- 두 가지 개념
	- 패키지 그 자체
		- 압축된 파일 하나. 메타데이터 포함됨
	- 도구(패키지 관리자)
		- 대상 시스템에서 해당 패키지를 처리해 앱을 설치하고 유지 관리
		- 보통 사용자 대신 저장소와 상호작용하고 패키지의 로컬 캐시 유지 관리

### RPM 패키지 관리자
- RPM 관리자는 레드햇에서 만들었지만 여러 배포판에서 널리 사용됨
- `.rpm` 파일은 리눅스 표준 베이스에서 사용되며 바이너리나 소스 파일 포함
- 패키지는 암호로 검증할 수 있고, 패치 파일을 통한 델타 업데이트 지원
- 다음이 RPM 사용
	- yum, DNF, Zypper
### 데비안 deb
- deb `.deb`는 데비안 배포판에서 시작됨
- 바이너리나 소스 파일도 포함할 수 있다
- `dpkg`처럼 종속성 관리가 없는 저수준 패키지 관리자와 `apt-get`, `apt`, `aptitude` 등의 고수준 패키지 관리자 포함해 많은 패키지 관리자가 deb 사용한다.

## 컨테이너
- 도커 덕분에 컨테이너는 2014년에 주류로 편입됨
- 그 전에도 컨테이너 도입 시도는 있었다
	- 리눅스 V서버, OpenVZ, LXC, lmctfy
- 이 방식들의 공통점은 네임스페이스, cgroup 등 리눅스 커널이 제공하는 기본 빌딩 블록으로 사용자가 애플리케이션 실행할 수 있게 한다는 점


- 도커는 기존 개념 혁신하고 두 가지 획기적인 요소를 도입
- 하나는 컨테이너 이미지 통해서 패키징을 정의하는 표준화된 방법, 또 다른 한 가지는 인간 친화적인 사용자 인터페이스
- 이는 OCI 핵심 사양의 기반이 되었다


- OCI 3가지 핵심 컨테이너 사양
	- 런타임 사양 : 운영과 수명주기 단계를 포함해 런타임이 지원해야 하는 것을 정의
	- 이미지 형식 사양 : 메타데이터와 계층을 기반으로 컨테이너 이미지가 구성되는 방식 정의
	- 배포 사양 : 컨테이너 이미지가 전달되는 방식, 컨테이너와 관련해 저장소가 효과적으로 동작할 수 있는 방식 정의


- 또 다른 개념은 불변성. 한 번 구성되면 사용 중에 변경할 수 없다는 의미
- 즉, 변경하려면 새로운 정적 구성과 새 리소스 생성해야 함
### 리눅스 네임스페이스
- 처음에 리눅스는 리소스에 대해 global view 가지고 있었음
- 프로세스가 리소스에 대해 local view를 가질 수 있도록 리눅스는 네임스페이스 도입
- 즉, 네임스페이스는 리소스 가시성에 관한 것이며 운영체제 리소스의 다양한 측면을 격리하는 데 사용할 수 있다
- 격리란 대부분 프로세스가 무엇을 보는지와 관련되어 있으며 보안 관점에서 볼 때 반드시 엄격한 경계는 아니다.
- 3가지 관련 시스템 콜
	- clone : 실행 컨텍스트의 일부를 부모 프로세스와 공유할 수 있는 자식 프로세스 만든다
	- unshare : 기존 프로세스에서 공유된 실행 컨텍스트 제거하는 데 사용
	- setns : 기존 프로세스를 기존 네임스페이스에 결합하는 데 사용


- 이 시스템 콜은 다양한 플래그를 매개변수로 사용하므로 새로 생성, 가입, 탈퇴하려는 네임스페이스를 세밀하게 제어할 수 있다.
	- CLONE_NEWNS, CLONE_NEWUTS, CLONE_NEWIPC, CLONE_NEWPID, CLONE_NEWNET, CLONE_NEWUSER, CLONE_NEWCGROUP

### 리눅스 cgroup
- cgroup은 프로세스 그룹을 구성하는 메커니즘 제공
- cgroup을 계층 구조와 함께 사용하면 시스템 리소스 사용을 제어할 수 있다
- 리소스 사용 추적도 가능하다.
- cgroup은 선언형 유닛으로, 컨트롤러는 특정 리소스 제한을 적용하거나 사용량을 보고하는 커널 코드로 생각하자
- v1, v2가 있다

#### cgroup v1
- 필요에 따라 새로운 cgroup과 컨트롤러 추가할 수 있는 애드혹 접근 방식을 사용할 수 있다
- 원래 있는 컨트롤러는 아래와 같다.


- CFS 대역폭 제어 : cpu cgroup
- CPU 사용량 정산 컨트롤러 : cpuacct cgroup
- cpusets cgroup : 작업에 CPU, 메모리 할당
- 메모리 리소스 컨트롤러 : 작업의 메모리 동작 분리
- 디바이스 화이트리스트 컨트롤러 : 디바이스 파일 사용 제어
- freezer cgroup : 배치 작업 관리
- 네트워크 분류기 cgroup : 패킷에 다른 우선순위 할당
- 블록 IO 컨트롤러 : 블록 I/O 조절
- perf_event 명령 : 성능 데이터 수집
- 네트워크 우선순위 cgroup : 네트워크 트래픽의 우선순위 동적 설정
- HugeTLB 컨트롤러 : HugeTLB 사용 제한
- 프로세스 번호 컨트롤러 : 특정 제한에 도달한 후 cgroup 계층이 새 프로세스 생성 중지할 때 사용

#### cgroup v2
- v1 교훈을 바탕으로 cgroup 완전히 다시 작성
- 일관된 구성, 사용은 물론 문서도 개선되었다
- 단일 계층 구조만 가지며, 모든 컨트롤러가 동일한 방식으로 관리된다

- CPU 컨트롤러 : CPU 주기의 분산 제어. 다양한 모델(weight, max)을 지원하고 사용량 보고 포함
- 메모리 컨트롤러 : 사용자 공간 메모리, dentry, inode 등의 커널 데이터 구조, TCP 소켓 버퍼 지원 등 다양한 제어 매개변수로 메모리 분산 제어
- I/O 컨트롤러 : 가중치 기반의 절대 대역폭, IOPS 제한으로 I/O 리소스 분산 제어, 바이트와 IOPS 읽기/쓰기 보고
- PID 컨트롤러 : v1 버전과 유사
- cpuset 컨트롤러 : v1 버전과 유사
- device 컨트롤러 : eBPF 위에 구현된 디바이스 파일 접근 관리
- rdma 컨트롤러 : RDMA 리소스 분산과 연결 제어
- HugeTLB 컨트롤러 : v1 버전과 유사


- v2에는 스칼라 리소스에 대한 리소스 제한과 추적 메커니즘 허용하는 기타 cgroup 있다
- `systemctl` 사용하면 리눅스 시스템의 모든 v2 cgroup을 트리로 볼 수 있다.
	- `systemctl status`
- 혹은 `systemd-cgtop`

### 쓰기 시 복사(CoW) 파일시스템
- CoW 파일 시스템은 빌드 시 사용되며 애플리케이션과 모든 종속성을 배포 가능한 독립 파일 하나로 패키징한다
- CoW 파일 시스템은 주로 bind mount와 함께 사용되며 종속성이 서로 다른 콘텐츠를 효율적으로 계층화

### 도커
- 도커는 빌딩 블록을 결합할 때 네임스페이스와 cgroup 같은 저수준 비트 관리의 복잡성을 숨겨서 사용하기 쉽게 만들었다
![](files/Pasted%20image%2020260905205421.png)
- 컨테이너 이미지
	- 실질적인 디렉터리인 JSON 파일과 계층의 메타데이터 포함하는 압축된 아카이브 파일
	- 도커 데몬은 필요에 따라 컨테이너 레지스트리에서 컨테이너 이미지를 가져온다
- 런타임 아티팩트로서의 컨테이너
	- 이 컨테이너는 필요에 따라 시작, 중지, 종료, 제거할 수 있다
	- 도커 데몬과의 상호작용에는 cli 사용하고 이 cli는 데몬에 명령을 보내고 데몬은 컨테이너 빌드, 실행과 같은 작업을 차례로 실행한다.
#### 컨테이너 이미지
- Dockerfile이라는 일반 텍스트 파일 형식 사용

#### 실행 컨테이너
- 대화형 입력이나 데몬으로 실행될 수 있다
- `docker run` 명령은 환경 변수, 노출할 포트, 마운트할 볼륨 등 런타임 입력 세트와 컨테이너 이미지 사용
- 이 정보를 사용해 도커는 필요한 네임스페이스와 cgroup 생성하고, 컨테이너 이미지에 정의된 애플리케이션을 시작한다.
