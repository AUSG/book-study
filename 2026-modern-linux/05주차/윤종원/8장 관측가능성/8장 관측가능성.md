## 기본 개요
### 관측가능성 전략
- 관측가능성에 대해 널리 확립된 전략 중 하나가 OODA 루프(Observe Orient Decide Act)
- 관측된 데이터를 기반으로 가설을 테스트하고 이에 따라 조치를 취하는 구조화된 방법, 시그널로부터 실행 가능한 통찰력을 얻는 방법을 제공한다.

### 용어
- 관측 가능성
	- 외부 정보를 측정하여 시스템의 내부 상태를 평가하는 것
- 시그널 유형
	- 기호적 수단(payload, log)이나 숫자 값, 이들의 조합을 통해 시스템 상태에 대한 정보를 보여주고 내보내는 다양한 방식
- 소스
	- 시그널을 생성하는 곳
- 목적지
	- 시그널을 소비, 저장, 추가적으로 처리하는 곳
- 텔레메트리
	- 소스에서 시그널을 추출하고 목적지로 전송하는 프로세스
	- 필터, 다운샘플링 등을 하는 에이전트를 쓸 때가 많다

### 시그널 유형
- 시그널은 추가 처리나 해석을 위해 시스템의 상태를 전달하는 방법
- 텍스트 페이로드, 숫자 페이로드로 구분한다.
#### 로그
- 사람이 사용할 수 있는 텍스트 페이로드가 있는 개별 이벤트
- 로그 내용을 자동화하기는 어렵지만 로그는 사람에게 매우 유용하므로 당분간 가장 강력한 시그널 유형으로 남을 가능성이 높다

#### 지표
- 샘플링된 숫자 데이터 포인트로 시계열을 형성한다
- 각각의 데이터 포인트는 차원이나 식별 메타데이터의 형태로 추가 컨텍스트를 가질 수 있다
- 일반적으로 원시 지표를 직접 사용하지 않고 일종의 집계나 그래픽 표현을 사용하고, 특정 조건이 충족되면 알림을 받기도 한다.
- 이는 운영 작업에 유용하며 문제 해결에도 유용할 수 있다.


- 카운터
	- 올라갈 수만 있다. 총 요청 수, 전송된 바이트 등등
- 게이지
	- 올라가거나 내려갈 수 있다. 메인 메모리, 실행 중인 프로세스 수 등
- 히스토그램
	- 값의 분포를 나타낸다.

#### 추적
- 런타임 정보의 동적 모음으로 디버깅뿐만 아니라 성능 평가에도 자주 쓰인다

## 로깅
- 개별 이벤트
	- 특정 이벤트가 발생했을 때 이를 공유하기 위함
- 텍스트 페이로드
	- 텍스트로 이루어져 있어 사람이 보기 편하다

- 구조적 관점
	- 로그 항목, 메시지, 행의 모음
		- 개별 이벤트에 대한 정보를 캡처
	- 메타데이터, 컨텍스트
		- 전역 범위뿐만 아니라 메시지 단위로 존재할 수도 있다
	- 개별 로그 메시지를 해석하는 방법을 보여주는 형식
		- 로그 부분과 의미 정의한다
		- 공백 혹은 JSON 스키마 등

- 로그로 인한 오버헤드는 피하는 편이 좋다

### Syslog
- 커널, 데몬, 사용자 공간까지 이르는 다양한 소스의 로깅 표준
- 네트워크 환경에 근간을 두고 있으며, 최근의 프로토콜은 배포 시나리오 및 보안 고려사항과 함께 RFC 5424에 정의된 텍스트 형식으로 구성된다.

![](files/Pasted%20image%2020260914193114.png)
- PRI : 메시지의 장비 유형(facility)과 심각도(severity)
- VER : Syslog 프로토콜 번호 (1만 가능하므로 보통 생략)
- TS : ISO 8601 형식으로 메시지 생성된 시각 표시
- HN : 메시지를 보낸 시스템 식별
- APP : 메시지를 보낸 애플리케이션 또는 디바이스 식별 
- PID : 메시지를 보낸 프로세스 식별
- MID : 메시지 ID


- 이 형식에는 각 요소가 `[]`로 묶인 구조화된 목록이 페이로드인 구조화된 데이터도 포함된다
- 일반적으로 로그 관리에는 `syslogd` 바이너리를 사용하지만 아래도 고려해보자
	- `syslog-ng`, `rsyslog`


- 등장한 지 꽤 오래되었지만 여전히 많이 쓰인다
- 하지만 `systemd`가 사실상 표준이 되면서 `systemd` 저널이 등장했다.

### journalctl
- `journalctl`은 바이너리 형식을 사용하여 로그를 저장
- 따라서 더 빠르게 접근할 수 있고, 공간도 덜 차지
- 그래서 `cat`, `grep` 등은 쓸 수 없지만 `journalctl` 쓰면 쉽다.

## 모니터링
- 모니터링이란 다양한 이유로 시스템과 애플리케이션 지표 캡처하는 것
- 작업에 소요되는 시간, 프로세스가 소모하는 리소스에 관심이 있을 수도 있고, 비정상 시스템의 문제를 해결해야 할 수도 있다
- 보통 두 가지 유형의 활동을 많이 한다.
	- 하나 이상의 지표 추적
	- 조건에 의거한 알림

### 디바이스 I/O와 네트워크 인터페이스
- `iostat` 쓰면 I/O 디바이스 모니터링할 수 있다.
- `ss`로 소켓 통계 덤프할 수 있다.
- `lsof`는 `list open files`의 약자이다. 네트워크 중심 뷰도 가능하고 프로세스 뷰도 가능하다.
- 혹은 `sar`, `perf` 등이 있다.

### 통합 성능 모니터
- `top` 등을 쓰면 적절한 인터페이스로 대부분의 리소스 값을 조회할 수 있다.
- `htop`, `atop`, `below` 등등
- `glances`, `guider`, `neoss`, `mtr`

### 계측
- 시그널, 특히 지표를 생성하기 위해 코드를 삽입할 수도 있는데
- 이를 일반적으로 계측(instrumentation)이라고 하며 두 가지 전략이 있다
- 자동 계측, 사용자화 계측

- StatsD는 좋지만 쿠버나 IoT 등에서는 풀 기반이나 스크레이핑 전략이 더 나은 접근 방법이다
- 애플리케이션이 지표를 노출하고, 에이전트는 메트릭을 어디로 보낼지 앱을 구성하지 않고 엔드포인트 호출해 메트릭을 검색한다.

## 고급 관측가능성
### 추적과 프로파일링
- 추적(tracing)이라는 용어는 여러 곳에서 많이 쓰인다
- 리눅스 맥락에서 보면 단일 시스템에서 추적이란 시간 경과에 따라 프로세스 실행을 캡처하는 것
	- 쿠버나 분산 시스템에서는 분산 추적을 많이 이야기한다.


- 단일 리눅스 시스템에는 다양한 데이터 소스가 있고, 다음을 추적 소스로 사용할 수 있다
	- 리눅스 커널
		- 커널 함수에서 가져올 수도 있고, 시스템 콜에 의해 트리거될 수도 있다
		- `kprobe`, 커널 tracepoint 등
	- 사용자 공간
		- 사용자 공간 프로브(`uprobe`)
- 혹은 `strace`, `perf`가 추적의 사용 예다.


- 앞으로는 eBPF가 추적을 구현하는 사실상 표준이 될 것으로 보인다
- 특히 사용자 지정(custom) 추적 사례가 더 그렇다
- 생태계가 풍부하고, 벤더사 지원도 날로 커지고 있다.


- 추적의 사용 사례 중 하나인 프로파일링은 자주 호출되는 코드 섹션을 식별한다
- `pprof`, `Valgrind`, flame graph 시각화 등이 있다.


- continuous profiling은 시간 경과에 따라 추적을 캡처하는 프로파일링 고급 버전

### 프로메테우스와 그라파나
- 프로메테우스나 그라파나 조합 쓰면 좋다
- node exporter 쓰면 CPU부터 메모리와 네트워크에 이르는 다양한 시스템 지표를 노출할 수 있다
- 이걸 프로메테우스로 스크랩하면 된다.
