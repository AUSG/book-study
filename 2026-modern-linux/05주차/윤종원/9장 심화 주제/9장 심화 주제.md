# 9장 심화 주제

## 프로세스 간 통신
- 파이프, 소켓, 공유 메모리 등 IPC 옵션이 많다
- 예를 들어 도커 데몬은 컨테이너 관리에 소켓을 쓴다.

### 시그널
- 원래 커널이 특정 이벤트를 사용자 공간 프로세스에 알리기 위한 방법으로 개발되었다
- 즉, 프로세스에 전송되는 비동기 알림
- 대부분은 시그널에 대해 리눅스가 제공하는 기본 동작 대신 커스텀 핸들러를 정의한다.

![](files/Pasted%20image%2020260914200929.png)

- 프로세스끼리 통신할 때 사용할 용도로 의미가 정의되지 않은 시그널(`SIGUSR1`, `SIGUSR2`)도 있고, 양쪽 당사자가 이 시그널의 의미에 동의하는 경우 비동기 알림을 보낼 수 있다
- 프로세스에 시그널을 보내는 일반적인 방법 중 하나가 `kill`


- `trap`으로 시그널을 처리할 수도 있다.
![](files/Pasted%20image%2020260914202227.png)

### 이름 있는 파이프
- `|`를 이름 없는 파이프(unnamed pipe)라고 한다
- 원하는 이름을 지정할 수 있게 한 파이프를 이름 있는 파이프(`named pipe`)라고 한다.
- 둘 다 일반 파일 I/O와 함께 동작할 수 있고, 선입선출 방식을 사용한다.
- 이름 없는 파이프와 달리 수명이 함께 사용하는 프로세스로 제한되지 않는다.
- 엄밀히는 이름 있는 파이프는 `pipefs`의 의사 파일시스템을 사용하는 파이프의 래퍼다.

![](files/Pasted%20image%2020260914202354.png)

- 사용하기 쉽지만 하나의 방향과 하나의 컨슈머만 지원해 제한적이다.

### 유닉스 도메인 소켓
- 단일 시스템에 대해 독점적으로 작동하는 소켓 중 하나다
- 양방향 다자간 통신 엔드포인트.
- 스트림 지향(SOCK_STREAM), 데이터그램 지향(SOCK_DGRAM), 시퀀스 패킷(SOCK_SEQPACKET) 등 세 가지 종류로 제공된다.
- 주소를 찾는 작업은 파일시스템 경로 이름을 기반으로 동작한다.


- 일반적으로는 프로그램 방식으로 도메인 소켓을 사용한다
- 하지만 시스템 문제를 해결할 때는 `socat` 도구를 사용할 수도 있다.

## 가상 머신
![](files/Pasted%20image%2020260914203233.png)
- CPU
	- 하드웨어 가상화 지원해야 한다
- 커널 기반 가상 머신
	- 리눅스 커널에서 찾을 수 있다
- 사용자 공간의 구성 요소
	- 가상 머신 모니터(VMM)
		- 가상 머신을 관리하며 QEMU와 Firecracker 같은 가상 디바이스를 에뮬레이트한다
		- 프로그래밍 방식으로 사용할 수 있으며 가상 머신 모니터 표준화를 목표로 하는 일반 API를 제공하는 `libvirt` 같은 라이브러리도 있다
	- 게스트 커널
		- 일반적으로 리눅스 커널이지만 윈도우일 수도 있다
	- 게스트 프로세스
		- 게스트 커널에서 실행

- 호스트 커널에서 네이티브하게 실행되는 프로세스는 게스트 프로세스와 격리된다.
- 즉, 일반적으로 호스트의 물리적 CPU와 메모리는 게스트 활동의 영향을 받지 않는다.
- VM에서 공격이 진행되어도 호스트 커널과 프로세스는 영향 받지 않는다
- 다만, rowhammer, Meltdown, Spectre 등 예외가 있을 수도 있다.

### 커널 기반 가상 머신
- Kernel-based Virtual Machine(KVM)
- AMD-V, Intel VT 등과 같이 가상화 확장을 지원하는 x86 하드웨어용 리눅스 네이티브 가상화 솔루션
- 코어 모듈(kvm.ko)과 아키텍처별 모듈(kvm-intel.ko, kvm-amd.ko) 등의 두 부분으로 나뉘어 있다.
- KVM에서 리눅스 커널은 하이퍼바이저 역할을 하며, 어려운 작업 대부분을 처리한다
- I/O 가상화를 허용하는 Virtio 같은 통합 드라이버도 있다
- 최근의 하드웨어는 일반적으로 가상화 지원한다
- KVM 관리하는 모던한 방법 중 하나는 파이어크래커를 사용하는 것
### 파이어크래커
- KVM 인스턴스 관리할 수 있는 가상 머신 모니터(VMM)
- 러스트로 작성되었고, AWS Lambda, AWS Fargate 등 서버리스를 위해 AWS에서 개발했다


- 동일한 물리적 시스템에서 멀티 테넌트 워크로드를 안전하게 실행하도록 설계되었다
- 이는 호스트에 HTTP API를 노출하는 마이크로 가상 머신을 관리해 사용자가 이 microVM을 시작, 쿼리, 중지할 수 있게 해준다
- 호스트에서 TUN, TAP 디바이스를 사용해 네트워크 인터페이스를 에뮬레이트하고 블록 디바이스는 Virtio 디바이스를 지원하는 호스트의 파일에 의해 지원된다.
- 이 외에도 `seccomp` 필터를 이용해 사용 가능한 호스트 시스템 콜을 제한한다.
- cgroup도 사용할 수 있다
- 관측가능성 관점에서 이름 있는 파이프를 통해 로그와 메트릭을 수집할 수 있다.

## 모던 리눅스 배포판
- 많이 쓰이는 것들
	- 레드햇 제품군(RHEL, Fedora, CentOS, Rocky)
	- 데비안 기반 제품군(Ubuntu, Mint, Kali, Parrot, Elementary)
	- SUSE 군(openSUSE, Enterprise)
	- Gentoo
	- 아치 리눅스


- 컨테이너에서는 기존 패키지 관리자가 다른 역할을 한다
- 대부분의 기본 컨테이너 이미지는 특정 리눅스 배포판에서 빌드되는 경향이 있다
- 종속성은 컨테이너 내에서 `.deb`, `.rpm` 패키지로 충족되지만 컨테이너 이미지는 그 위에 모든 애플리케이션 수준의 종속성을 패키지화한다


- 또한 시스템에 점진적으로 변경사항을 적용하는 건 큰 도전이다
- 그래서 모던 배포판은 더 불변성에 초점을 맞추고 있다
- 기본 개념은 구성이나 코드가 변경될 때마다 실행할 컨테이너 이미지와 같은 새로운 아티팩트를 생성한다
	- 실행 중인 시스템을 변경하지 않는다

### 레드햇 엔터프라이즈 리눅스 코어OS
- 시스템 업데이트를 위한 이중 파티션 스키마
- 패키지 관리자가 없다. 즉 모든 앱은 기본적으로 컨테이너에서 실행된다
- `etcd` 등이 이 생태계에서 개발된 도구들


- 레드햇은 코어 OS 인수 후 코어 OS 리눅스를 레드햇의 자체 프로젝트 아토믹과 병합할 계획 발표
- 인수 합병으로 레드햇 엔터프라이즈 리눅스 코어 OS 탄생
- 단독으로 쓰이지 않고 OpenShift Container Platform 배포 환경에서 쓰인다
